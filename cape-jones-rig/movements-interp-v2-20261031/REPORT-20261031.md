## What v2 is, plainly
Every v2 frame is a fresh render through the v7c rig builder (build_interp_v2.py,
same ball-centre pivot math as build_ginyu_force.py / build_inbetween.py):
joint angles interpolated between key configs, slow-in/slow-out (smoothstep),
a labelled BREAKDOWN at the middle inbetween of each transition (arc bulge
+10deg on the largest-moving arm upper, middle frame only), overshoot 5%
beyond the fight key then settle (serve-to-guard only), top-arm layer = union
of endpoint top sets (face/cowl snap preserved). NO whole-picture blending
anywhere in the v2 sequences. A v2 that blended two pictures at once would
FAIL the 2026-10-31 19:16 CDT correction; this one does not.

## Ghosting measured, v1 vs v2, serve->guard mid frame (method in measure_ghost.py)
Silhouette = mean-abs distance from grey-128 > 40. Edge = silhouette pixel
with a non-silhouette 4-neighbour. Double-edge ratio = mid edge count /
mean(key edge counts); ~1 = one figure, ~2 = two figures superimposed.
Wash = pixels in serve-xor-guard silhouette where the mid pixel sits halfway
between that key's pixel and grey (diff to grey 20..120 AND diff to key >20);
exactly what a 50% crossfade produces in a non-overlap region.
- v1 mid (frame 012, crossfade t=0.5): silhouette 78,271 px, edge 15,072,
  double-edge ratio 1.32, wash 25,525 / 26,532 xor px = 96.2% washed.
  That is the ghost Mars saw: almost every non-overlap pixel is a halfway blend.
- v2 mid (frame 015, rig BREAKDOWN t=0.5): silhouette 86,264 px, edge 11,462,
  double-edge ratio 1.01, wash 4,561 / 26,532 = 17.2%.
  Ratio 1.01 = ONE figure, no double edge. Residual 17.2% wash is not a
  second figure: in xor regions the rig mid carries a solid different-colour
  piece (e.g. black cape where the key had white suit), which trips the
  wash test's diff-to-key >20 condition at anti-aliased edges and colour
  boundaries. Viewed frames confirm it: frame 015 is one solid figure.
- Rig keys vs originals (silhouette IoU): serve 0.996, guard 0.996
  (same builder, as expected). Fight vs the approved fighting-pose file
  0.782 — because the fight key here is a measured estimate, NOT the
  approved file's config (see "still owed").
